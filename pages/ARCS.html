Advanced Recovery Code Standard

With the massive amounts of data routinely used and stored in the modern day, corruption is routine and expected. Although widespread and well-supported, it is just one of many schemes used to protect data against corruption.

ARCS is a standard specifying a scheme for packaging any piece of data with a recovery code capable that helps in error detection and allows the original bits to be recreated in case of corruption. Digital files sometimes incorporate a built-in ARCS field, with the help of which they undergo routine integrity checks and repair. Other times, for files which do not support having a built-in ARCS field, separate arcs files can be generated to provide them with redundancy. The standard is made such that it can be easily added to file types and other arbitrary information which originally did not support it.

It incorporates a number of algorithms, most notably Reed-Solomon error correction codes. In the future will likely add an option to pick between (or maybe use both) reed-solomon and Low-Density Parity Checks (I expect that LDPC would be much better for massive files thanks to linear complexity - Reed-Solomon appears to be completely unuseable for error correction on files zetabytes in size such as human brain emulations even for a quettabithertz level compute cluster, and even for particularly large AI models stays prohibitively expensive - but I should fix the bitflip cost calculation of Reed-Solomon first)

Field structure

The ARCS field is at least 800 bits long, plus however long the recovery data is. It can be included in the same piece of data multiple times - if the area they are meant to protect is overlapping then their error correction codes will be calculated together like one long code split into parts. All the parts which describe lengths of data or locations are encoded as 128 bits long unsigned base2 integers, allowing encoding of vastly more data than is needed for most use cases as a form of future proofing. Including multiple ARCS fields increases the chance that at least one will remain readable, allowing data to be recovered even if there is otherwise no indication where the file begins and ends, and doing so is the reason for ARCS fields with zero reed-solomon bits being valid inclusions. For that use case there are dedicated parts of the ARCS field which point at the beginning of the previous field and the beginning of the next field - they always point at the first bit of the field so that the parsing algorithm knows where to start, meaning that having a previous field less than 800 bits away is not valid since it would necessarily overlap, but is not necessarily considered an error and will simply be ignored instead of trying to find another field there.

The protection provided by the Reed-Solomon bits implicitly extends to the field itself, as all the values in the field are set first and then the RS bits are calculated, protecting the whole span between the start of preceding data and the end of following data, including the ARCS field itself. This is allowed by the Reed-Solomon error correction algorithm, as it does not fundamentally distinguish between error correction bits and data bits.

Reference redundancy level values

  • 1E-13% redundancy across the whole file: provides a number of redundancy bits equivalent to the expected number of random bit flips after a terran year of data storage on a typical solid state hard drive. By the common reliability standards for dedicated data storage devices, the average data corruption accumulated over the course of a terran year should be no more than 1 in 1 quadrillion bits. This is purely a reference value and generally not used.
  • 1E-10% redundancy across the whole file: provides theoretically enough redundancy to fix 1000 years worth of accumulated bit rot on standard hardware with 50% probability. It should also provide good protection from mild radiation-induced data corruption such as that which can happen as a result of various solar events. Routine checks and repairs using this level of redundancy practically guarantee that data will not accumulate random bit flips and that it may be returned to pristine condition even after laying forgotten in cold storage, but will not protect against outright hardware failure. Fairly common for AI sapients, as the computational requirements of their minds mean that most already have access to sufficient computational power that a check and repair operation on a piece of data as big as them might take between a second and a kilosecond. At the extreme end a digitized human mind might need to go dormant for a few kiloseconds to perform the full check and repair, making it a chore to be done each week or month, or for those more cautious included as an automatically performed part of sleeping if the given transhuman happens to still do such.
